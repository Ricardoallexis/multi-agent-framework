# Changelog

Notable changes to the public project are documented here. The project uses `M-B-F` product versions and a separate PEP 440 version for the Python package. Because the roadmap is a living document, each release also lists the roadmap changes it publishes under **Roadmap**.

## [Unreleased]

### Added

[`docs/TEAMS.md`](docs/TEAMS.md) covers `team.yaml`, validation, versions and approval, decision records and the organization chart in Python, HTTP, CLI and the GUI, linked from the README, API, GUI and roadmap pages.
- Teams view in the GUI: an «Equipos» section (`#teams`, `#teams/<bundle>`) lists the bundles with a `team.yaml`, their approved version and the latest pending proposal. Opening one shows the organization chart as nested lists with each position's status in words, the `reviews` and `delegates_to` links apart, a forest notice, the Mermaid text with a copy button, and the versions with their diff. The pending proposal can be approved or rejected after a confirmation, with an optional note; the server records the decision as `user:operator` on the `gui` channel, whatever the page sends. Routes under `/gui/api/teams`, behind the GUI token.
- Team organization chart (S6.B1, S6.B2): `services.teams.org_chart(bundle, version_id=None)` returns one position per role (who holds it, whom it reports to, who reports to it, and `occupied`, `vacant` or `pending`), the root or an explicit forest, the `reviews` and `delegates_to` links apart, and a Mermaid `flowchart TD`. By default it shows the approved team; a later proposal marks the positions it adds or changes as `pending` and those it removes with `pending_removal`. Without an approved version it shows the latest proposal, draft or `team.yaml`, all `pending`. A role with two managers (`multiple_managers`) or a `reports_to` cycle is `invalid_definition`. The same chart is at `GET /api/v1/teams/{bundle}/org-chart` and `multiagent team org-chart BUNDLE [--version ID] [--mermaid]`.
- Team approval with versions (S6.A3): `services.teams` keeps versions of a bundle's `team.yaml` in the system database (migration 015, `team_versions`). `propose` validates the team as `validate_bundle` does and saves a `proposed` (or `draft`) version with its canonical JSON and sha256; a team equal to the approved version is refused as `invalid_request` (`no_changes`). Only a `user:` actor can approve or reject, and only a proposed version (`invalid_state` 409 otherwise); a decided version does not change again, and the current team is the last one approved. Each answer carries a structural diff against the approved version: roles, members, assignments and relationships added, removed and changed, with the changed fields. A new run of a bundle with an approved team records its id, number and sha256 in a `team_version_bound` event; later proposals or edits of `team.yaml` do not change it. The same operations are under `/api/v1/teams` and `multiagent team propose|submit|approve|reject|show|list|approved` (actor `user:local` by default). No run uses the team yet: role per step comes with S6.C1.

- Evaluation view in the GUI (S10.C1, S10.C2): a read-only «Evaluación» view (`#evaluation`, in the section list) lists the evaluation sets that have saved runs with their latest score, Mock or live, and state against the baseline (`Regresión`, `Sin línea base` or `Al día`). Opening a set shows its saved runs and compares the latest one with the baseline: cases `regressed`, `improved`, `changed` and `unchanged`, cases found in only one run, and what changed in the fingerprint. A regression is a result, not an error. It reads `GET /gui/api/evaluations`, `/evaluations/runs`, `/evaluations/runs/{id}` and `/evaluations/comparison?set_name=` behind the GUI token, and it cannot run a set or set a baseline. This closes the evaluation stage. See `docs/GUI.md` and `docs/EVALUATION.md`.
- Evaluation regressions (S10.C2): every evaluation run, Mock or live, is saved in the system database (migration 017, tables `evaluation_runs` and `evaluation_baselines`) with its fingerprint, report and score, and `meta.evaluation_run_id` names it. A set can have one baseline, which setting it again replaces. Comparing two runs of the same set (the base defaults to the baseline) classifies each case as `regressed` (it passed and no longer does, or its score drops by more than the threshold), `improved`, `changed` (its checks or its fingerprint differ) or `unchanged`, lists cases found in only one run apart, and says what changed in the fingerprint: prompt or agent, workflow, models and providers, or the set (`set_changed`). The threshold is `EVAL_REGRESSION_THRESHOLD` (default 0.0, from 0 to 1), and a request can override it. Use `services.evaluation.list_runs`, `get_run`, `set_baseline`, `get_baseline` and `compare`, the routes under `/api/v1/evaluations/runs`, `/baselines/{set_name}` and `/compare`, or `multiagent eval runs [--set NAME]`, `show ID`, `baseline set ID`, `baseline show NAME` and `compare CANDIDATE [--base ID] [--threshold X]`, which exits 3 on a regression, 0 without one and 1 on an error. Comparing runs of different sets, or setting a run of another set as baseline, fails with `evaluation_set_mismatch` (409). See `docs/EVALUATION.md`.
- Team validation with least privilege (S6.A2): when a bundle has a `team.yaml`, validating the bundle also checks the team against its workflows. Errors: a role names an unknown output contract (`team_unknown_contract`) or skill (`team_unknown_skill`), or a role assigned to a step lacks a permission that the impacts of the step's tools need (`team_permission_missing`). Warnings: a permission no assigned step uses (`team_permission_unused`), a step whose agent has no role in the team (`team_agent_unassigned`) and a tool that cannot be resolved (`team_tool_unresolved`, left out of the permission check). A member with two roles gets the union of their permissions. Tools are resolved, never run. `services.definitions.validate_bundle` and `POST /api/v1/bundles/{name}/validate` return errors as `422` with `details.team` and warnings as `200` with `warnings`; `multiagent bundle-validate` prints each finding with its severity and location and exits 1 on errors, 0 on warnings alone. A bundle without a team validates as before. The example `general` bundle drops permissions its tool-less workflows never use.
- External step output (S13.C2): a run waiting for a `human_guided` step, or at a review checkpoint, can take a step output produced outside the framework in two steps. Preview validates the output against the step contract and the attached evidence (PNG, JPEG, WebP, MP4, WebM, plain text, JSON and JSON Lines, checked by extension and leading bytes, with per-file and total size limits) and stages it outside the run, which it does not change; it expires after `EXTERNAL_PREVIEW_TTL_SECONDS` (default 900). Confirm, once and by a `user:` actor, completes the waiting step, or adds a new attempt that stays under review, and stores the evidence under framework-generated names, a manifest with the SHA-256 of the output and of each file, and a receipt with who, channel and time, as run artifacts, with an `external_output_confirmed` event. Native and mock declare the `external_output` capability. Use `services.runs.external_output_preview` and `external_output_confirm`, `POST /api/v1/runs/{id}/external-output/preview` and `/confirm`, or `multiagent external-output preview RUN_ID --output FILE [--evidence FILE ...]` and `confirm RUN_ID PREVIEW_ID`. In the GUI, the run detail has an «Salida externa» block while the run waits: paste the JSON output, pick evidence files, preview them with their SHA-256 hashes, confirm and see the receipt; its routes under `/gui/api` fix the actor (`user:operator`) and the channel, and a body that names either is rejected. Evidence is never executed or sent to a prompt. No migration is needed. See `docs/HUMAN_GUIDED.md`.
- Deterministic function steps (S5.D1): a workflow step may name a function registered by trusted host code (`function: core.merge_outputs`, with literal `arguments`) instead of an agent and a prompt. The function gets the run inputs and the validated outputs of earlier steps, read-only, and its result is validated against the step's contract and stored as an artifact; native and mock run it the same way, with no provider call, call guard or usage record. Validation reports `unknown_function` and rejects provider fields on such a step; a run that sets a routing preference or execution mode for it fails with `function_step_option_invalid` (422) through Python, HTTP, the GUI and the CLI. Workflow inputs, prompt and routing previews, attempts, run reports and the GUI show the step as a function. The `general` bundle has an example, `collect_summary`. See `docs/FUNCTION_STEPS.md`.
- Evaluation sets for workflows, agents and prompts (S10.C1): a set may declare a `target` (a workflow, an agent or a prompt with its version) besides its cases, inputs and deterministic checks, and every report carries a fingerprint of the target, the set and the models used. Run one with `services.evaluation.run`, `multiagent eval run <file> [--format json|markdown] [--live]` or `POST /api/v1/evaluations/run`. Mock is the default and runs on a temporary data directory with no worker, deleted afterwards, so it never touches the runs of the system database; its report has the statuses but no run ids. `--live` (or `"live": true`) runs a workflow set on the server: each case is an ordinary run, with usage, budgets and egress as usual, executed by the server's worker; the report has the run ids, a case that does not stop within `EVAL_LIVE_TIMEOUT_SECONDS` (default 900) fails as `timeout`, and without a running worker the request fails with `eval_live_worker_unavailable` (409). See `docs/EVALUATION.md`.
- Several workers with controlled concurrency (S4.D1): a worker claims a queued run atomically in one SQLite transaction and holds it with a lease (`worker_id` and `heartbeat_at`, renewed while it runs), so several processes can share one database without running the same run twice. `WORKER_CONCURRENCY` (default 1, as before) sets how many runs one process executes at a time; `WORKER_MAX_ACTIVE_TOTAL` and `WORKER_MAX_ACTIVE_PER_PROJECT` cap the active runs across processes, in total and per project; `WORKER_LEASE_SECONDS` and `WORKER_SHUTDOWN_WAIT_SECONDS` set the lease and how long a stopping worker waits for its runs. On start and from time to time a worker recovers only runs whose lease has expired, so it no longer interrupts the runs of another live worker, and it releases stale claims of queued runs. `multiagent worker [--concurrency N]` runs a worker alone against the configured database. No migration is needed.
- Decision register (S13.B2): proposals and decisions with who proposed and who decided, a state (`proposed`, `accepted`, `rejected`, `superseded`, and `expired` when an accepted decision's `valid_until` has passed), a validity period and links to a run, step, attempt, task, team or project, kept in SQLite (migration `016_decisions.sql`).
